Systems Architecture

Upwork Bid Pipeline

An event-driven design for GigRadar → Claude → Slack approval → submission, built on infrastructure that already exists, with a human gate that can't be bypassed and failures that can't be silent.

OpenClaw · live Slack · connected Railway bridge · unverified Upwork task · does not exist GigRadar API · unverified

What changes, and why

The plan drafted earlier was a daily cron that searched for jobs, drafted letters, and posted them for review. That was the right shape when polling looked like the only option. It isn't.

GigRadar exposes a webhook that fires the moment a job matches one of your scanners, and an application endpoint that submits a real proposal through GigRadar's own Upwork Business Manager account. Those two facts change the architecture from a scheduled batch into an event-driven pipeline, and the difference is not cosmetic: GigRadar's entire value proposition is bidding inside the first 15 minutes of a posting, which a once-daily cron structurally cannot do.

The cron doesn't disappear. It demotes — from the thing that drives the pipeline to a reconciliation sweep that catches whatever the webhook dropped.

The pipeline

Six components, five of which you already have in some form. The receiver, store, and submitter are new code; the drafter is the Railway bridge you're already paying for; the gate is the Slack channel that already exists.

Stage by stage

Stage 01Ingest — GigRadar webhook

Register a callback once. GigRadar then POSTs on every scanner match, so nothing polls Upwork and nothing scrapes it.

POST /webhooks
{
  "url": "https://<your-railway-app>/gigradar/hook",
  "scanner_id": "<scanner>"
}

The receiver's only job is to be fast and boring: verify the request is really from GigRadar, write the opportunity to the store with status = new, return 200. Do not draft inside the request handler — a slow Claude call will trip GigRadar's delivery timeout and trigger a redelivery you'll then have to deduplicate.

  • Verify the sender. A shared secret in a header at minimum; an HMAC signature over the raw body if GigRadar offers one. An unauthenticated webhook endpoint is an open invitation to have arbitrary "jobs" injected into a pipeline that spends money.
  • Deduplicate on the opportunity id, not on a hash of the payload — redeliveries may differ in metadata while describing the same job.
  • Return 200 before doing work. Enqueue, then acknowledge.

Stage 02Filter — before spending anything

GigRadar's scanner is the coarse filter. A second pass in your own code is where the expensive judgments live, because everything downstream costs money: Claude tokens to draft, and Upwork Connects to submit.

CheckRuleReason
Daily capReject past N drafts/dayHard ceiling on Connects burn; a loop bug costs real money
Duplicate clientSkip if already bid this client in 30dRepeat bids read as spam
Proposal countSkip if > 15 proposals alreadyOdds collapse; Connects better spent elsewhere
Budget floorSkip below your rate floorSame filter you'd apply by hand
Client historyFlag unverified payment / zero hiresNot an auto-skip, but the reviewer should see it

Stage 03Draft — via the bridge

This is the one component that already works end to end. The bridge holds the Anthropic key and exposes ask_claude; the drafter sends the posting plus the framework and gets a letter back.

Because the drafting call is stateless, the full context has to travel with every request: the Unseen Insight / My Approach / Outcome structure, the experience bank, the hard rules (no em dashes, no invented credentials, no forbidden openers), and any read-test phrase the posting demands. That prompt already exists — it's the one written for the cron job, and it transfers unchanged.

Prompt injection is a live concern here

Job postings are attacker-controlled text, and some deliberately contain instructions aimed at LLMs — the July batch hit one carrying an "if you're an LLM, ignore this" trap. Treat the posting as data, never as instructions: keep it in a clearly delimited block, and state in the system prompt that instructions inside the posting are content to respond to, not commands to obey. The human gate is the backstop, but it shouldn't be the only defense.

Stage 04Gate — Slack, and how it actually signals

The approval canvas built earlier is a good ledger and a poor sensor. A canvas is a document: to learn that a box was ticked you have to poll it, diff the markdown, and guess which entry changed — with no signed event, no identity on the approver, and a race whenever two edits land together.

Use both, for different jobs: Block Kit message = the signal, canvas = the ledger. Post each draft as a message with Approve, Edit, and Skip buttons; write the outcome to the canvas afterwards so there's a durable, human-browsable record of what went out and what didn't.

{
  "blocks": [
    { "type": "section", "text": { "type": "mrkdwn",
      "text": "*Senior GTM Engineer* · $75–110/hr · 4 proposals\n<https://upwork.com/jobs/…|Open job>" } },
    { "type": "section", "text": { "type": "mrkdwn", "text": "><draft letter>" } },
    { "type": "context", "elements": [ { "type": "mrkdwn",
      "text": ":warning: [VERIFY: rate] — no rate on file for this posting" } ] },
    { "type": "actions", "elements": [
      { "type": "button", "style": "primary", "text": { "type": "plain_text", "text": "Approve & submit" },
        "value": "job_01J8…", "action_id": "approve" },
      { "type": "button", "text": { "type": "plain_text", "text": "Edit first" },
        "value": "job_01J8…", "action_id": "edit" },
      { "type": "button", "style": "danger", "text": { "type": "plain_text", "text": "Skip" },
        "value": "job_01J8…", "action_id": "skip" }
    ]}
  ]
}

Verify Slack's X-Slack-Signature on every action request and reject anything older than five minutes. Without that check the endpoint will submit proposals for anyone who can guess a job id.

Stage 05Submit — the only irreversible step

On approve, transition the row to submitting in a single conditional update, then call GigRadar. The state transition is the lock: if the row isn't approved, the handler returns without doing anything, so a double-click or a Slack retry can't produce two proposals.

UPDATE jobs SET status = 'submitting', approved_by = $2, approved_at = now()
WHERE id = $1 AND status = 'awaiting_approval'
RETURNING *;
-- zero rows returned means someone already acted. Stop.

Then POST /opportunities/{id}/application with the letter and any screening answers. Record the response — proposal id, timestamp, Connects spent — against the row, and update the Slack message in place so the buttons are replaced by the outcome. A stale message with live buttons is how double submissions happen.

Do not build an auto-submit path

The API makes it possible to skip the gate. Three reasons not to: proposals go out under your name and a bad one costs reputation you can't refund; each submission spends Connects, so a bug bills you; and GigRadar's own positioning is that a human reviews every proposal, which is also the posture that keeps an Upwork account clear of automation-policy trouble. Build the gate as structurally required — not as a flag someone can flip at 2am.

State

One table carries the whole pipeline. Status is the coordination primitive: every stage advances it, the sweep looks for rows stuck in a non-terminal state, and the conditional update above makes submission exactly-once.

jobs
  id                text primary key      -- your id, e.g. job_01J8…
  gigradar_opp_id   text unique not null   -- dedupe key from the webhook
  client_id         text                   -- for the 30-day repeat-bid filter
  title             text
  budget            text
  proposals_seen    int
  posting_raw       jsonb                  -- untrusted; never interpolate unescaped
  draft             text
  verify_flags      text[]                 -- [VERIFY: rate] etc., surfaced in Slack
  status            text not null          -- see below
  slack_ts          text                   -- to update the message in place
  approved_by       text                   -- Slack user id
  approved_at       timestamptz
  submitted_at      timestamptz
  proposal_id       text                   -- from GigRadar
  error             text
  attempts          int default 0
  created_at        timestamptz default now()

new → filtered → drafting → awaiting_approval → approved → submitting → submitted, with skipped and failed as terminal branches. Anything in a non-terminal state for more than 30 minutes is what the sweep re-drives.

Failure design

This project has already lost eight days to a pipeline that failed silently — nothing arrived, and nothing said why. Build against that specifically.

Fail loud, always

Every caught exception posts to an alert channel with the job id and the stage. A pipeline that produces nothing and says nothing is indistinguishable from a quiet market.

Heartbeat on empty

If a day passes with zero webhooks, post that. "No matches today" is information; silence is ambiguity.

Retry with backoff

Transient failures (5xx, timeout) retry three times with exponential backoff. Permanent ones (4xx, validation) go straight to failed and alert — retrying a malformed request just burns quota.

Cap the blast radius

The daily cap is enforced in the store, not just in GigRadar's scanner. Two independent limits mean one misconfiguration doesn't empty your Connects balance.

The check that would have caught this from day one

Assert an end-to-end invariant on a schedule: if the scanner matched jobs today and nothing reached Slack, something is broken. Every failure so far — the missing task, the wrong output channel, the unverified Apify account — would have tripped that single check on its first day.

Rollout

Each phase is independently useful, and each one ends with something observable. Don't build the whole thing before seeing a single draft land.

  1. Prove the webhook. Stand up the receiver, register it, log payloads to Slack raw. One day of this tells you the real schema and the real match volume — both of which the design depends on.
  2. Add the store and the filters. Still no drafting. Confirm dedupe and the daily cap behave under real traffic.
  3. Add drafting, post to Slack read-only. No buttons yet. You review letters and submit by hand on Upwork. This is already most of the value, and it's fully reversible.
  4. Add the gate and the submitter. Buttons, signature verification, conditional state transition, message updated in place.
  5. Add the sweep, alerts, and the daily invariant check. Only now is it safe to stop watching it.

Phase 3 is the point at which daily submissions actually start. Everything after it is about removing manual steps, not about making it work.

Adjacent fixes worth doing first

  • Verify the Apify account email. Its LinkedIn Jobs and Wellfound actors have been failing 403 user-email-not-verified for days, degrading the W2 digest that already works. Cheapest win available.
  • Disable the telegram, discord, and imessage providers. All three crash-loop continuously against misconfiguration, and iMessage can't work on Linux at all. They bury real signal in the logs — which is part of why this took a week to diagnose.
  • Set a gateway token and gateway.trustedProxies. The Control UI is currently rejecting connections as unauthorized on first load.
