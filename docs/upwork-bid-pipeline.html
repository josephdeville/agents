Systems Architecture

Upwork Bid Pipeline

A design for Upwork API → Claude → Slack approval → you, built inside what Upwork's automation policy permits, on infrastructure that already exists, with a human gate that can't be bypassed and failures that can't be silent.

What changes, and why

An earlier draft of this document routed discovery through a GigRadar webhook and submission through GigRadar's application endpoint, which posts a real proposal via their own Upwork Business Manager. That design optimised for speed: bid inside the first fifteen minutes, because that is where the win rate lives.

It optimised for the wrong constraint. Upwork's automation policy permits AI-drafted proposals only where a person reviews, edits, and clicks submit on each one, and names auto-submission at scale as a bannable violation. Upwork's public GraphQL API has no mutation to submit a proposal or spend Connects, so any tool that submits programmatically is operating outside the sanctioned surface. The account risk lands on the freelancer, not the vendor.

So the architecture changes at both ends and nowhere else. Discovery moves onto an Upwork-issued API key obtained through their review process. Submission moves to the human. Everything between those two points survives unchanged — the filters, the drafter, the state model, the exactly-once transition, the failure design. What was previously called phase 3 of the rollout, "post to Slack, submit by hand," turns out to have been the terminal state all along rather than a waypoint on the way to something more automated.

The cron is no longer a demoted reconciliation sweep. Without a webhook it is the primary driver again, polling an approved endpoint on a documented rate limit.

There is a second-order effect worth stating up front, because it removes work rather than adding it. Once the human submits, the approval signal has no downstream consumer — nothing is blocked waiting to hear it. That collapses stage 04 from a signed-callback integration into a bot token and an emoji, and takes the Slack app, the request URL, the signing secret and the reachable host with it.

The permitted line

Upwork publishes the boundary directly, in Use bots and other automation properly. It is unusually specific, and it maps almost box for box onto the pipeline below.

PermittedProhibited
Job alerts and routing: collecting new postings and forwarding them to Slack, email, or a dashboard, without auto-submitting Auto-submitting proposals at scale, or sending bids without human review
Using AI to draft proposals, provided a person manually reviews, edits, and clicks submit for each one Driving the site with OAuth2 tokens or session cookies from a script
CRMs, task boards, and dashboards that track proposals, contracts, milestones, and performance Calling website pages instead of approved API endpoints
Automation running on an API key issued after Upwork reviews the account and the stated use case Exceeding rate limits, or background polling that resembles scraping
The human click is the compliance boundary, not a preference

Every earlier version of this design treated the approval gate as prudence: Connects cost money, proposals carry your name, a bug at 2am is expensive. Those reasons still hold, but they are now secondary. The gate is the specific condition under which Upwork permits AI-drafted proposals at all. Removing it does not make the pipeline faster and riskier; it makes it prohibited. Build it as structurally required, with no flag that disables it.

Sourcing caveat

The pipeline

Five components. The poller and store are new code and neither is large. The drafter is the Railway bridge you already pay for. The gate is the Slack channel that already exists. The handoff is a Slack message with a link in it. Nothing here needs to hold an Upwork password, nothing touches a browser, and nothing in the whole design accepts an inbound request — every arrow above originates on your side.

Stage by stage

Stage 01Ingest — the approved API, on your own key

Upwork does not push. There is no webhook, so this stage is a poller, and the distinction that keeps a poller legitimate is what it polls: an approved GraphQL endpoint on a key Upwork issued you, within the documented rate limit. Polling web pages, or driving the site with a session cookie, is the prohibited version of the same shape.

Getting the key is therefore the first task in the whole project, and it gates everything else. Upwork reviews both the account and the stated use case, so the application is worth writing carefully; a description that mirrors their own allowlist language is describing a system they have already said is permitted.

  • Poll on a documented interval, not as fast as the limit allows. Five minutes is ample. The win-rate advantage of bidding early is real but it is not worth looking like a scraper, and a five-minute poll still puts you inside the first hour on almost every posting.
  • Deduplicate on Upwork's job id. The same posting will come back on every poll until it is filtered or drafted.
  • Persist the raw posting with status = new and treat it as untrusted text from there on. It is attacker-controlled.
  • Back off on errors rather than retrying tightly. Repeated hammering after a 429 is exactly the pattern the policy calls out.
Until the key exists, there is no compliant discovery path

Not a soft blocker. Every alternative — scraping search pages, a browser extension harvesting results, a third party polling on a shared credential — falls on the prohibited side. If the key application is refused, the honest answer is that discovery stays manual and only drafting is automated, which is still most of the value.

Stage 02Filter — before spending anything

The search query is the coarse filter. A second pass in your own code is where the expensive judgments live, because everything downstream costs something: Claude tokens to draft, Connects to submit, and your attention to review. That last one is the scarcest of the three, and the filters exist mostly to protect it.

CheckRuleReason

Stage 03Draft — via the bridge

This is the one component that already works end to end. The bridge holds the Anthropic key and exposes ask_claude; the drafter sends the posting plus the framework and gets a letter back.

Because the drafting call is stateless, the full context has to travel with every request: the Unseen Insight / My Approach / Outcome structure, the experience bank, the hard rules (no em dashes, no invented credentials, no forbidden openers), and any read-test phrase the posting demands. That prompt already exists — it's the one written for the cron job, and it transfers unchanged.

Prompt injection is a live concern here

Job postings are attacker-controlled text, and some deliberately contain instructions aimed at LLMs — the July batch hit one carrying an "if you're an LLM, ignore this" trap. Treat the posting as data, never as instructions: keep it in a clearly delimited block, and state in the system prompt that instructions inside the posting are content to respond to, not commands to obey. The human gate is the backstop, but it shouldn't be the only defense.

Stage 04Gate — Slack, with nothing inbound

Moving submission to the human changed what this stage is for, and the change is easy to miss. When approval triggered an automated submission, the signal needed to be fast, signed, and unambiguous, because a submitter was blocked on it. Nothing is blocked on it now. You read the letter, you go to upwork.com, you submit. Approval and submission are the same human act.

So the question is no longer what is the most reliable signal. It is what is the cheapest way to record something that already happened — and the answer is a different mechanism than the previous version of this document recommended.

MechanismInfrastructureApprover identityWeakness
Canvas checkboxPoll + diff the markdownNoneMust guess which entry changed; races when two edits land together
Block Kit buttonSlack app, request URL, signing secret, reachable hostYes, in the payloadAll of that infrastructure, to serve a signal nothing waits on
Emoji reactionBot token. Nothing inbound.Yes, in reactions.getLearned one poll interval late, which costs nothing here

Post each draft as an ordinary message carrying the Job ID and the letter. A person reacts once they have acted: white_check_mark submitted, x skipped, pencil2 needs an edit first. A job on a timer reads reactions and writes the outcome to the ledger.

# post — one outbound call
POST https://slack.com/api/chat.postMessage
  { "channel": "C0BNXNUL0QZ", "text": "<job id + letter>" }
  → { "ok": true, "ts": "1788747638.570449" }   # store ts on the row

# read — one outbound call, on a timer
GET https://slack.com/api/reactions.get?channel=C0BNXNUL0QZ&timestamp=<ts>
  → reactions: [ { name: "white_check_mark", users: ["U07HPV9QPKP"] } ]

That is the entire integration. No public endpoint, no signature verification, no app interactivity configuration, and nothing that breaks when a tunnel closes or a host sleeps. The bot token is the same one the existing weekday digest already posts with.

Identity comes free, which the canvas never managed

reactions.get returns the user ids who reacted, so the ledger records who acted and when without inference. That was the one thing the canvas could not do and the main reason buttons looked necessary. It turns out not to have required buttons.

Do not pre-seed the reactions

Adding the three emoji to each message so they are one click instead of two seems helpful and quietly breaks the design. "Any reaction present" is the signal; a bot-added reaction is indistinguishable from a human one unless every read filters the bot's user id, which is a correctness burden on every future reader of this data. Leave the message bare.

The canvas keeps its job. It is a durable, human-browsable log of what went out and what did not, which is what a document is good at. It simply is not the sensor.

Stage 05Handoff — making the human step short

The system does not submit. Its last job is to compress the human's work to a few seconds, because that is what makes daily volume survivable: ten proposals a day is five minutes of clicking, not an afternoon.

On approve, take the same conditional update as before. It is still the lock, and it still makes the transition exactly-once, but what it now guards is the handoff rather than an API call.

UPDATE jobs SET status = 'approved', approved_by = $2, approved_at = now()
WHERE id = $1 AND status = 'awaiting_approval'
RETURNING *;
-- zero rows returned means someone already acted. Stop.

Then replace the Slack message in place with a handoff card carrying three things: the final letter in a copyable block, a direct link to the job's apply page on Upwork, and a single Mark submitted button. The person opens the link, pastes, reads it once more in context, and clicks submit on Upwork themselves.

You lose the submission receipt, so the ledger depends on the human

This is the one genuine cost of the permitted design and it is worth naming. When the system submitted, it got back a proposal id and a Connects figure and could write them down with certainty. Now nothing observes the submission, so submitted is a state only a person can assert. Two consequences: Mark submitted is a real part of the workflow rather than bookkeeping, and any row sitting in approved for more than a day is ambiguous rather than stuck. Have the sweep ask about those in Slack instead of re-driving them.

Do not build an auto-submit path, and do not buy one

Upwork's public API has no proposal mutation, so every product that offers auto-submission reaches the site some other way. That is the prohibited side of the line, and the account it suspends is yours rather than the vendor's, reportedly without appeal. The reasons that already applied still apply: proposals go out under your name, each one spends Connects, and a bug at 2am bills you for its mistakes. Build the gate as structurally required, with no flag that turns it off.

State

One table carries the whole pipeline. Status is the coordination primitive: every stage advances it, the sweep looks for rows stuck in a non-terminal state, and the conditional update above makes submission exactly-once.

jobs
  id                text primary key      -- your id, e.g. job_01J8…
  upwork_job_id     text unique not null   -- dedupe key; the same posting recurs on every poll
  client_id         text                   -- for the 30-day repeat-bid filter
  title             text
  budget            text
  proposals_seen    int
  posting_raw       jsonb                  -- untrusted; never interpolate unescaped
  draft             text
  verify_flags      text[]                 -- [VERIFY: rate] etc., surfaced in Slack
  status            text not null          -- see below
  slack_ts          text                   -- to update the message in place
  approved_by       text                   -- Slack user id
  approved_at       timestamptz
  submitted_at      timestamptz            -- asserted by a human, not observed
  submitted_by      text                   -- Slack user id who clicked "Mark submitted"
  error             text
  attempts          int default 0
  created_at        timestamptz default now()

new → filtered → drafting → awaiting_approval → approved → submitted, with skipped and failed as terminal branches. The submitting state is gone: nothing machine-driven happens between approval and submission any more, because the step in between is a person.

That changes what the sweep can do. Anything stuck before approved is a system fault and gets re-driven. Anything sitting in approved is waiting on a human, so re-driving it is meaningless — the sweep should ask in Slack instead, and let the row age out to skipped after a day, since a posting that old is not worth Connects anyway.

Failure design

This project has already lost eight days to a pipeline that failed silently — nothing arrived, and nothing said why. Build against that specifically.

Fail loud, always

Every caught exception posts to an alert channel with the job id and the stage. A pipeline that produces nothing and says nothing is indistinguishable from a quiet market.

Heartbeat on empty

If a day passes with zero webhooks, post that. "No matches today" is information; silence is ambiguity.

Retry with backoff

Transient failures (5xx, timeout) retry three times with exponential backoff. Permanent ones (4xx, validation) go straight to failed and alert — retrying a malformed request just burns quota.

Cap the blast radius

The daily cap is enforced in the store, independently of whatever the search query returns. A drafting loop can waste tokens; it cannot spend a Connect, because no code path spends Connects at all.

The check that would have caught this from day one

Assert an end-to-end invariant on a schedule: if the scanner matched jobs today and nothing reached Slack, something is broken. Every failure so far — the missing task, the wrong output channel, the unverified Apify account — would have tripped that single check on its first day.

Rollout

Each phase is independently useful, and each one ends with something observable. Don't build the whole thing before seeing a single draft land.

  1. Apply for the API key. Nothing downstream is compliant without it, and review takes as long as it takes. Do this before writing any code, not alongside.
  2. Draft by hand, in Slack. While review is pending, run the whole thing manually: you paste a posting, Claude drafts against the framework, the letter lands in the approval queue, you submit. Zero infrastructure, and it produces submissions this week rather than next month.
  3. Prove the poller. Once the key lands, poll and log matches to Slack raw. A day of this tells you the real field shapes and the real volume, both of which the filters depend on.
  4. Add the store and the filters. Still no drafting. Confirm dedupe and the daily cap behave under real traffic.
  5. Add drafting and the gate. Buttons, Slack signature verification, conditional state transition, handoff card replacing the message in place.
  6. Add the sweep, alerts, and the daily invariant check. Only now is it safe to stop watching it.

Phase 2 is the point at which daily submissions actually start, and it needs nothing built. Everything after it removes manual steps from a process that is already running, which is the right order: if the manual version does not produce wins, automating it just produces losses faster.

Adjacent fixes worth doing first

  • Verify the Apify account email. Its LinkedIn Jobs and Wellfound actors have been failing 403 user-email-not-verified for days, degrading the W2 digest that already works. Cheapest win available.
  • Disable the telegram, discord, and imessage providers. All three crash-loop continuously against misconfiguration, and iMessage can't work on Linux at all. They bury real signal in the logs — which is part of why this took a week to diagnose.
  • Set a gateway token and gateway.trustedProxies. The Control UI is currently rejecting connections as unauthorized on first load.
