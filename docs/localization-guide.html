Terms worth being precise about

These get used interchangeably and shouldn't be. The distinction decides who owns a task.

i18n — Internationalization

Engineering work. Removing the assumption that text is English, dates are MM/DD/YYYY, and layout flows left-to-right. Done once, in code.

l10n — Localization

Adapting the internationalized product for one locale: translation, currency, imagery, legal copy. Done per locale, mostly not by engineers.

Locale ≠ language

A locale is language + region + optional script: pt-BR differs from pt-PT in vocabulary and currency; zh-Hans and zh-Hant differ in script.

The practical rule: if a string is baked into a component, that's an i18n bug and it's yours. If a string is translated badly, that's an l10n issue and it goes to the translator.

Phase 01

Audit for hardcoded text

Before choosing a library, find out how big the problem is. Hardcoded strings are the obvious target, but the expensive finds are the assumptions that don't look like text at all.

What to grep for

# User-facing strings in JSX
rg '>[A-Z][a-z]{2,}[^<]*<' --type tsx

# Hand-rolled date and currency formatting
rg 'toLocaleDateString\(\)|\$\{.*\.toFixed\(2\)\}|MM/DD|DD/MM'

# Concatenated sentences — these break every language with different word order
rg '["`].*\s\+\s|\+\s*["`]'

# Physical CSS properties that won't mirror
rg 'margin-left|margin-right|padding-left|padding-right|text-align:\s*(left|right)'

Assumptions that aren't strings

  • Name fields. firstName + lastName fails for mononyms, patronymics, and cultures that order family name first. Prefer a single fullName unless you have a concrete reason.
  • Address forms. A required "State" dropdown blocks most of the world. Postal codes are not all numeric, and not all countries have them.
  • Sorting. Array.sort() sorts by code point, which puts Ä after Z. Swedish wants that; German doesn't.
  • Text expansion. German runs 30–35% longer than English; Japanese runs shorter but taller. Fixed-width buttons will break.
  • Calendars and week start. Not every locale starts the week on Sunday, and not every user is on the Gregorian calendar.
Cost of skipping this

An audit takes a day. Discovering the name-field assumption after it's in three services, two schemas, and a partner API costs considerably more, because by then it's a migration rather than a decision.

Phase 02

Design the key namespace

Translation keys are an API between engineering and translators, and they age badly if chosen carelessly. Two rules carry most of the value: keys describe location and purpose, and one key means one sentence in one context.

Do

{
  "checkout": {
    "summary": {
      "title": "Order summary",
      "itemCount": "{count, plural,
        one {# item} other {# items}}",
      "submit": "Place order"
    }
  }
}

Don't

{
  "orderSummary": "Order summary",
  "submit": "Submit",
  "ok": "OK",
  "error1": "Something went wrong"
}

Flat keys collide. A shared submit gets reused in a context where the correct German verb is different, and now one of the two screens is wrong.

Conventions worth writing down

  • Namespace by feature, then by component, then by element: checkout.summary.title.
  • Never reuse a key across contexts to save a line. Duplication in the source file is cheaper than a mistranslation.
  • One base language file is the source of truth, committed to the repo. Everything else is generated or pulled.
  • Give translators context. Most formats support a description field — use it: "submit": { "message": "Place order", "description": "Button on the final checkout step" }.
  • Never build a key at runtime (t('status.' + code)). Static extraction can't see it, so it silently ships untranslated.
Phase 03

Write messages in ICU

String concatenation is the single most common i18n defect, because it hardcodes English word order and English plural rules into the code. ICU MessageFormat moves both into the translatable message, where a translator can change them.

// Broken: assumes 2 plural forms and English clause order
const label = count + (count === 1 ? ' item' : ' items') + ' in your cart';

// Correct: the whole sentence is one translatable unit
t('cart.itemCount', { count });

The forms you'll actually use

FormSyntaxUse for
Plural {count, plural, =0 {No items} one {# item} other {# items}} Any count. Use =0 when the empty case reads differently.
Select {gender, select, female {She} male {He} other {They}} replied Grammatical gender, roles, plan tiers.
Ordinal {rank, selectordinal, one {#st} two {#nd} few {#rd} other {#th}} Rankings, positions, dates as ordinals.
Number {price, number, ::currency/USD} Currency and compact notation inside a sentence.
Date {when, date, medium} Dates embedded in prose.
Why plural categories matter

English has two plural forms. Arabic has six (zero, one, two, few, many, other); Polish has four; Japanese has one. A ternary in your code can only ever express two. ICU lets each language file declare the forms that language actually needs, which is why the rule is never branch on count in code.

Interpolating markup

Don't split a sentence to wrap part of it in a tag — the split point moves between languages. Pass the element as a value instead:

// message: "Read our {terms} before continuing."
t.rich('legal.notice', {
  terms: (chunks) => <a href="/terms">{chunks}</a>
});
Phase 04

Format with Intl, never by hand

The Intl namespace is built into every runtime you target and carries the full CLDR dataset. Anything you write yourself will be a worse, staler subset of it.

APIHandlesExample
Intl.NumberFormatDecimal separators, grouping, currency placement, compact notation1.234,56 € vs €1,234.56
Intl.DateTimeFormatField order, month names, 12/24-hour, calendar systems, time zones14/03/2026 vs 3/14/2026
Intl.RelativeTimeFormat"3 days ago" with correct plural and tense per languagehace 3 días

// Construct once, reuse — the constructor is the expensive part
const price = new Intl.NumberFormat(locale, {
  style: 'currency',
  currency: 'EUR',
});
price.format(1234.56);   // "1.234,56 €" in de-DE

// Truncation that doesn't split a grapheme cluster
const seg = new Intl.Segmenter(locale, { granularity: 'grapheme' });
const chars = [...seg.segment(text)].map(s => s.segment);
const clipped = chars.slice(0, 40).join('');
Storage vs display

Store canonical, display localized. Timestamps as UTC ISO-8601, money as minor units plus a currency code, never as a formatted string. Formatting is a presentation concern; the moment a formatted value enters your database you've lost the ability to re-render it for a different reader.

Phase 05

Detect and route locales

Pick one routing strategy and apply it consistently, because it determines your URLs, your caching, and your SEO.

Subpath — /de/pricing

The default choice. Shareable, cacheable, indexable, one deployment. Use unless you have a reason not to.

Subdomain — de.site.com

Useful when locales are operated by different teams or need separate infrastructure.

ccTLD — site.de

Strongest local signal and sometimes a legal requirement. Most expensive to run.

Resolution order

  1. Explicit locale in the URL — always wins.
  2. User preference persisted on the account.
  3. Cookie from a previous manual switch.
  4. Accept-Language header, negotiated against supported locales.
  5. Documented default.
import { match } from '@formatjs/intl-localematcher';
import Negotiator from 'negotiator';

const SUPPORTED = ['en', 'de', 'ja', 'ar'];
const DEFAULT = 'en';

export function resolveLocale(request) {
  const url = new URL(request.url);
  const fromPath = url.pathname.split('/')[1];
  if (SUPPORTED.includes(fromPath)) return fromPath;

  const cookie = request.cookies.get('locale')?.value;
  if (SUPPORTED.includes(cookie)) return cookie;

  const headers = { 'accept-language': request.headers.get('accept-language') ?? '' };
  const wanted = new Negotiator({ headers }).languages();
  return match(wanted, SUPPORTED, DEFAULT);
}
Don't geolocate by IP alone

Location is not language. A traveller in Tokyo, an expatriate, and anyone behind a VPN all get the wrong answer. IP is acceptable as a last-resort hint that surfaces a dismissible "View this page in Japanese?" banner — never as a silent redirect.

Tell search engines

<link rel="alternate" hreflang="en" href="https://site.com/en/pricing" />
<link rel="alternate" hreflang="de" href="https://site.com/de/pricing" />
<link rel="alternate" hreflang="x-default" href="https://site.com/en/pricing" />

Set <html lang> and <html dir> from the resolved locale on every response. Screen readers switch pronunciation on lang, so getting it wrong degrades accessibility as well as SEO.

Phase 06

Support right-to-left

Arabic, Hebrew, Persian, and Urdu mirror the entire interface, not just the text. If you write CSS in logical properties from the start, RTL costs almost nothing; retrofitting it later means auditing every stylesheet.

What logical properties won't fix

  • Directional icons. Arrows, chevrons, and undo glyphs must mirror. Media transport controls (play, fast-forward) must not.
  • Box shadows and gradients. The offsets are physical; set them per direction.
  • Bidirectional runs. A Latin brand name or a number inside Arabic text needs isolation, or punctuation jumps to the wrong end. Use <bdi> or unicode-bidi: isolate.
  • Charts and timelines. Whether a time axis mirrors is a product decision. Decide it explicitly rather than letting CSS decide for you.
/* Icons that should mirror */
[dir="rtl"] .icon-arrow { transform: scaleX(-1); }

/* Isolate a bidirectional run so punctuation stays put */
<p>تم الإرسال بواسطة <bdi>@joe_deville</bdi>.</p>
Cheap early, expensive late

Adopting logical properties before you support any RTL locale costs one lint rule and no runtime code. Doing it after Arabic ships costs a full visual regression pass across every screen.

Phase 07

Wire the translation loop

Translation is a pipeline, not an event. If a developer has to remember to email a spreadsheet, translations go stale within two sprints.

The loop

  1. Extract. A parser scans source for keys and writes the base-language file. Run it in CI so drift between code and file is caught, not tolerated.
  2. Push. On merge to main, new and changed source keys go to the TMS automatically.
  3. Translate. Translators work in the TMS, with the description field and, ideally, a screenshot for context.
  4. Pull. Completed translations come back as a PR, reviewed like any other change.
  5. Gate. CI fails the release if a locale marked as launched is missing keys.
# .github/workflows/i18n.yml
name: i18n
on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci

      # Extraction must be a no-op; if it isn't, someone added a key by hand
      - run: npm run i18n:extract
      - run: git diff --exit-code locales/en.json
        # Fails with: "run npm run i18n:extract and commit the result"

      # Every launched locale must be complete
      - run: npm run i18n:validate -- --locales de,ja,ar --fail-on-missing
Pick a source of truth and defend it

Either the repo owns the base file and the TMS owns translations, or the TMS owns everything. Both are workable. What isn't workable is editing translated files by hand and syncing from a TMS — the two overwrite each other, usually the night before a launch.

Phase 08

Test and gate in CI

Most localization bugs are visual and only appear in a locale nobody on the team reads. Automate the classes you can, and make the rest cheap to eyeball.

Pseudo-localization

The highest-value technique, and it needs no translators. Generate a fake locale that transforms the base language: accent every character, pad the string by 40%, and bracket it. Then run the app in it.

"Order summary"  →  "[Ǫřδεř šůmmářγ ~~~~~~]"
  • Anything still in plain ASCII is a hardcoded string that escaped extraction.
  • Anything clipped or overflowing will break in German.
  • Missing brackets mean a string was split and concatenated.

What to assert automatically

  • Key parity across launched locales — no missing keys, no orphans.
  • ICU messages parse, and placeholder names match between base and translation.
  • Plural categories present for each target language, not copied from English.
  • No physical CSS properties in new stylesheets (lint rule).
  • Snapshot rendering of key screens in one LTR and one RTL locale.
The failure that looks like success

Most i18n libraries fall back to the key or the base language when a translation is missing, so a broken build renders as readable English and passes every smoke test. Log fallbacks in development and count them in CI, or missing translations will reach production silently.

Pitfalls that survive review

These pass code review because they're correct in English.

Concatenation

t('deleted') + ' ' + count + ' ' + t('files') hardcodes English word order. One key, one full sentence.

Runtime keys

t(`error.${code}`) is invisible to extraction. Map codes to literal keys explicitly.

Translated identifiers

Never translate enum values, API fields, or anything used in a comparison. Translate the label; keep the value.

Text baked into images

Untranslatable and unindexable. Use real text over the image, or export per locale.

Locale-dependent case

'I'.toLowerCase() is 'ı' in Turkish. Never uppercase or lowercase for comparison without 'en-US' as an explicit argument.

Fixed-size containers

Buttons sized to the English label clip in German. Let content size the box; set a min-width, not a width.

Naive truncation

slice(0, 40) splits emoji and Devanagari clusters into replacement characters. Use Intl.Segmenter.

Assumed currency

Locale doesn't determine currency. A user in de-DE may be billed in USD. Carry the currency code with the amount.

Pre-merge checklist

For any PR touching user-facing text or layout.

  • No hardcoded user-facing strings; every one goes through t().
  • No sentence built by concatenation or a ternary on count.
  • Keys are static literals, namespaced by feature, with a description for translators.
  • Counts use ICU plural; gendered or role-varying copy uses select.
  • Dates, numbers, currency, and lists go through Intl, with an explicit locale.
  • New CSS uses logical properties; no margin-left, text-align: left, or physical inset.
  • Directional icons mirror; media controls don't.
  • Interpolated user content in a bidirectional context is wrapped in <bdi>.
  • Extraction is a no-op — the base file is committed and current.
  • Checked in pseudo-locale: nothing clipped, nothing untranslated, nothing split.
  • Checked in one RTL locale at the affected screens.
  • Stored values are canonical (UTC, minor units, currency code) — not formatted strings.
